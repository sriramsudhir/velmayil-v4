# Velmayil POS — Architecture & Coordination Contract

Offline-first Windows desktop POS. **Electron 44 + TypeScript + React + built-in SQLite (`node:sqlite`)**. No native modules.
Single authoritative **Business Profile** (shop name/logo/etc.) consumed by every module — never copy shop info into modules or templates.

## Layout
```
src/shared/            cross-process contracts (money, permissions, ipc, types) — foundation-owned, additive edits only
src/main/core/         App context, snapshot, lookup  (Agent 1 owns; others do NOT edit)
src/main/db/           driver, migrate, migrations/NNN_*.ts  (Agent 1 owns infra; each agent owns its migration range)
src/main/modules/<m>/  one folder per main-process module: index.ts exports `order` and `register(app)`
src/preload/           one generic bridge: window.velmayil.call(service, method, args)
src/renderer/lib/      api.ts (call()), module.ts (registry), session.tsx
src/renderer/ui/       design system (Agent 9 owns; keep exports/props backward compatible)
src/renderer/shell/    app frame (Agent 9)
src/renderer/modules/<m>/index.tsx   exports `module: ModuleDef` { id, nav[], routes[] } — auto-discovered, no central edits
tests/<module>/*.test.ts             vitest (node). Helpers: tests/helpers.ts  (createTestApp, actAs)
```
Modules and migrations are auto-discovered via `import.meta.glob` → **no agent ever needs to edit a shared registry file.**

## Hard rules
1. **Money** = integer paise. **Tax rate** = integer basis points (1800 = 18 %). **Timestamps** = epoch ms (UTC). Never floats for money. Qty = integer.
2. **Table ownership — writes only by the owner; reads (SQL) of any table are fine.** `app.moveStock()` is the ONLY way to change stock (all agents may call it).
3. **Migrations**: new file `src/main/db/migrations/<NNN>_<name>.ts` exporting `migration`. Never edit `001_core.ts` (ask Agent 1 / the integrator). Version ranges: A1 002–099, A2 100–199, A3 200–299, A4 300–399, A5 400–499, A6 500–599, A7 600–699, A8 700–799, unit codes 900–999. Additive only (ALTER TABLE ADD COLUMN, CREATE TABLE/INDEX).
4. **Services**: write a class in `modules/<m>/service.ts`; in `register(app)` create it, `app.provide('<m>', svc)` for cross-module use and `app.expose('<m>', { method: (args, app) => ... })` for the renderer. Each exposed method must `app.requirePermission(...)` (except public ones listed in `core/app.ts` PUBLIC) and validate input with zod. Throw `AppError(code, message)`.
5. **Multi-step writes** (sale, purchase, return…) run inside ONE `app.db.transaction`, including stock, audit (`app.audit`) and sync (`app.enqueueSnapshot`). **Printing/IO happens only AFTER commit.** A print failure must never roll back or repeat a sale.
6. **Sync**: every create/update of a syncable entity (has `uuid`) calls `app.enqueueSnapshot(table, id, childSpecs?)` in the same transaction. Snapshots carry `refs` (uuid-based FKs) so other terminals can resolve ids. Sales are immutable/append-only; catalog + profile are last-writer-wins by `updated_at`/`version`.
7. **Historical documents**: `sales.profile_version_id` / `sale_returns.profile_version_id` pin the business-profile version at the time of sale. Reprints use that version’s shop name/logo/address (policy: `settings.reprint_profile_policy` = `original` (default) | `current`). Profile edits create a NEW row in `business_profile_versions` (never UPDATE old versions).
8. **No hard-coded shop names** anywhere (code, templates, tests fixtures aside). Templates use `{{shop.display_name}}` etc.
9. **File ownership**: edit only files in your own directories (list below). Need something from another owner? Use their public service API as documented here; if the API is missing, write the request to `docs/requests/<from>-to-<owner>.md` and code against the documented contract — the integrator resolves it. Never duplicate tables/services/types/components; create a shared abstraction in your own area and mention it in your final report.
10. **Do not run `npm install`** (deps are preinstalled and managed by the integrator: react, react-router-dom, jsbarcode, qrcode, exceljs, zod, vitest, @playwright/test). Do not edit package.json, configs, or other agents’ files.
11. **Quality gate for every task**: `npm run typecheck` (ignore errors in files you don’t own that are clearly mid-edit by others), `npm test -- <your folder>`, then `npm run build` when UI changed. Fix before moving on. Write real tests that execute behaviour (DB-backed), not just compile checks.

## Live data
Every IPC `app.call(service, method)` that writes (SQLite `total_changes()` differs before/after) emits `{service, method, ts}` on the in-process bus: `app.onChange(listener) => unsubscribe`, `app.emitChange(entity)` for explicit use. Writes made outside `app.call` (inbound sync apply, background jobs) are caught by `app.startChangeWatcher()` (1 s poll of `total_changes()`, started in `main/index.ts`) and surface as service `'sync'`. `main/index.ts` coalesces events (`coalesceChanges`, 50 ms) and pushes them to every window on `LIVE_CHANNEL` (`shared/ipc.ts`); preload exposes `window.velmayil.onChange(cb) => unsubscribe`. Renderer: `useLiveRefresh(['catalog','pos'], reload)` (`renderer/lib/live.ts`) calls `reload` (debounced 150 ms) on an event from a listed service (events from `'sync'` always match) or when the window regains focus. Any list screen should use it so edits made on another screen/window/synced terminal appear within about a second.
Barcode readers: three input paths feed ONE pipeline. (1) Keyboard-wedge readers (the normal case): the always-focused billing scan box (`data-scanbox`, `lib/scanInput.ts`) takes the code + Enter/Tab at ANY speed; `lib/scanner.ts` `attachScanner` is the global fallback for other focus (burst detector with adaptive timing, CR+LF guard, Alt-code/keypress path, layout/Caps/NumLock repair, residue removal for text/number/textarea/contenteditable/select). (2) Web Serial (`lib/serialScanner.ts`) and (3) WebHID (`lib/hidScanner.ts`, HID POS reports) as optional hubs. All end in `useScanner(onScan)` -> `pos.scan`, which uses `app.lookup.byScan` (exact code first, then `modules/pos/codes.ts` spellings: UPC/EAN/GTIN/ITF, dropped check digit, zero padding, GS1, AIM `]E0`, Code 39 stars, case, alias barcodes). `byCode` stays exact (duplicate/validation checks). Main-process device access (serial/HID chooser + the single device-permission handler) lives in `modules/pos/deviceAccess.ts`; never call `setDevicePermissionHandler` anywhere else. Settings > Scanner has the "Detect my reader" wizard (`analyzeCapture`) and a Windows device report (`pos.scannerDevices`). OS-level tests: `tests/e2e/scanner-os.spec.ts` + `tests/e2e/tools/sendkeys.ps1` (SendInput).
## Unit codes
Owner rule: every physical unit of a product gets its own code `PREFIX-NNNN` (`SPK-0001`). When a code is scanned: not in the active list -> add it; already there -> warn "duplicate entry" (`src/shared/scanList.ts`: `createScanList`, `normalizeUnitCode`, `formatUnitCode`, `parseUnitCode`; the server applies the same rule: a code twice in one bill/transfer/return is rejected as `UNIT_DUPLICATE`).
- **Data** (migration 900): `products.track_units`, `products.unit_prefix` (2-8 chars A-Z0-9, UNIQUE NOCASE, frozen once units exist unless its 9999 codes are used up); `product_units` (uuid, variant_id, prefix, seq, `code` UNIQUE upper-case, status `in_stock|sold|returned|void`, sale_id, sale_item_id, purchase_id, location_id, void_reason; never deleted, code immutable); `unit_sequences(prefix,last_seq)`; `stock_count_units`. Triggers keep unit codes out of barcode / alias / SKU space; a prefix that would collide with an existing barcode/SKU `PREFIX-dddd` is refused (`PREFIX_CLASH`).
- **Invariant**: for a tracked variant `stock_levels.qty` (per location) == number of units with status `in_stock`/`returned` at that location. All stock paths keep it; `inventory.verifyLedger()` returns `unitMismatches` and `ok:false` when it breaks. Suffix is sequential per prefix and gap-free (rolled back with the transaction); at 9999 generation stops with `AppError('CONFLICT', ..., {code:'UNIT_LIMIT_REACHED'})` (never a 5th digit); give the product a new prefix (`units.setTracking`) to continue.
- **Service `units`** (`app.get<UnitsService>('units')` + renderer service `units`; errors are `AppError` with `details.code`): `setTracking({productId, trackUnits, prefix?, backfill?, discardUnits?})` (catalog.edit; enabling codes all existing stock), `suggestPrefix({name, productId?}) -> {prefix}`, `generate({variantId, count, purchaseId?, reason?, locationId?}) -> {codes, prefix, firstSeq, lastSeq}` (inventory.adjust; only for stock that has no code yet), `resolve({code}) -> null | {unit:{id,code,status,variantId,saleId}, variant}`, `list({variantId?, productId?, status?, search?, locationId?, limit, offset}) -> {rows,total}`, `counts({variantId}) -> {in_stock,sold,returned,void}`, `markVoid({codes, reason}) -> {voided, codes}` (writes off units and reduces stock in the same transaction), `countReport({countId}) -> {scanned, missing, unexpected, locationId}`.
- **Scan**: `app.lookup.byScan` / `pos.scan` resolve a unit code to its variant; the result's `unit` is then an OBJECT `{id,code,status,variantId,saleId}` (the measure string stays in `unitOfMeasure`; for ordinary barcodes `unit` is still the string). `pos.scan` throws `CONFLICT 'Unit SPK-0003 is already sold'` (`details.code:'UNIT_NOT_AVAILABLE'`, `details.status`) for sold/void units. A normal barcode of a tracked product returns `trackUnits:true`.
- **Sales**: `completeSale` lines take `unitCodes` (REQUIRED for tracked variants, `length === qty`, no duplicates in the bill, each unit available); units become `sold` + linked (`sale_id`, `sale_item_id`) with the stock movement in the same transaction; `voidSale` puts them back `in_stock`; `createReturn` items take `unitCodes` (required for lines sold with codes): `restock:true` -> `in_stock` (+stock), else `void`. `getSale` items carry `unitCodes`. A replayed `requestId` returns before touching units.
- **Inventory**: `purchases.create` / `inventory.adjust` (increase) auto-generate codes (`items[].unitCodes` / `unitCodes`; `generateUnits:false` skips, backfill with `units.generate`); `adjust` (decrease), `purchases.returnCreate` and `inventory.transferCreate` take `unitCodes` for tracked variants (transfers move `location_id`); `purchases.cancel` voids the purchase's units. Stock counts: `countScan` with a unit code adds it unless already scanned (`duplicate:true`), `unexpected:true` when not in stock at the count location; `countApply` voids missing units (reason `count`) and returns `missingUnits`/`unexpectedUnits`.
- **Catalog**: `catalog.save` accepts `trackUnits`, `unitPrefix`, `discardUnits`; `get`/`list` return `trackUnits`, `unitPrefix`.
- **Sync / multi-POS**: every unit change queues a `product_units` snapshot (uuid, refs to variant/sale/purchase/location). Inbound apply (`sync/apply/units.ts`) is idempotent by uuid, newer `updated_at` wins for status/links, applying a unit bumps the local `unit_sequences` so an online terminal keeps issuing fresh numbers. Terminal-safe strategy = conflict reporting: two terminals that generate the same prefix while offline can pick the same suffix; the later arrival is detected (same code, other uuid), logged in `sync_conflicts` (`duplicate_key`) and the local unit is kept (never overwritten). Stock movements sync separately.

Spreadsheet: Products > Spreadsheet uses `catalog.gridList` + `catalog.bulkUpdate({rows:[{variantId?, key?, patch}]})` (one transaction, all-or-nothing, per-row errors in `error.details.rowErrors`; barcode is only touched when `patch.barcode` is present).

## Deleting sales
`pos.voidSale` keeps the bill (status `void`); **`pos.deleteSale({ saleId, reason, approval? }) -> { ok, saleId, invoiceNo, total, stockRestored }`** removes it for good ("Delete order" on the Dashboard's Recent sales card and in Sales history; shared dialog `renderer/modules/pos/DeleteSaleDialog.tsx`). It is the one exception to "sales are immutable".
- **Permission** `pos.delete` (Owner `*`, default Manager; migration 110 adds it to existing roles that hold `pos.void`). Approval works exactly like a void: a user without `approvals.grant` needs a manager (`approval.approvalId` from `auth.verifyApprover` with action `pos.delete`, or approver credentials). `reason` is required (3+ chars). Unknown sale -> `NOT_FOUND`.
- **One transaction**: stock back -> tombstone -> rows deleted -> audit -> sync op. Stock: a bill that is not void gives back, per line, `qty - already returned` through `app.moveStock` (type `void`, note `Deleted <invoice>`; unit-coded lines through `units.restoreSaleItem`, so only units still `sold` return to `in_stock` at the location they left). A return already restocked or wrote off its goods and a void already restored everything, so those are never restored twice. Every unit of the bill loses `sale_id` / `sale_item_id`; returned / void units keep their status. `stock_levels == in-stock units` (`inventory.verifyLedger()`) holds afterwards.
- **Removed**: `sale_return_items`, `sale_returns`, `sale_payments`, `sale_items`, the `sales` row and the `print_log` rows of the invoice / its return numbers (`purgeSale()` in `pos/service.ts`, the only code that hard-deletes a bill). **Kept**: `stock_movements`, `audit_log` (entity `sale`, action `delete`; `old` = compact copy of the bill with items, payments, returns; `new` = reason, approver, stock restored), `approvals`, the customer. Invoice / return numbers are never reused. Shift summaries, reports and the dashboard are computed from the tables, so the bill simply drops out (the dashboard history fingerprint includes the tombstone count).
- **Guard**: the `trg_*_no_delete` triggers of migration 002 still refuse every hard delete; migration 110 re-creates them so they let a row go only when its sale has a row in **`deleted_sales(uuid PK, invoice_no, total, deleted_at, deleted_by, deleted_by_name, reason, origin_device)`**. The tombstone is written first and never removed.
- **Sync**: queued as entity `sales`, op `delete` (`saleDeletePayload`); `resyncAll` re-sends all tombstones. Inbound (`sync/apply/sales.ts`) purges the local copy, records the tombstone (even when the bill never arrived) and writes an audit entry; it does NOT move stock, because the deleting terminal's restore movements travel as ordinary `stock_movements` (applied once by uuid). Later snapshots of a tombstoned bill, of its return notes, or of units still pointing at it are skipped / applied without the link, so a deleted bill never comes back. The reference server needs no change (ops are opaque to it). Known limit (same as two offline voids of one bill): if two terminals delete, or one voids and one deletes, the SAME bill while both are offline, each restores the stock; correct it with a stock adjustment.

## Barcode numbering
Barcodes the app generates for products (form "Generate", `assignBarcode`, `generateMissingBarcodes`, `autoBarcode` on save, new spreadsheet rows) come from ONE allocator, `CatalogService.nextBarcode()`; pure rules live in `modules/catalog/barcode.ts` (`checkNumbering`, `formatInternalBarcode`, `parseInternalBarcode`).
- **Settings** (edited only through `catalog.saveSettings({barcodeMode, barcodePrefix, barcodeWidth})` / Products > Barcode numbering, validated as a combination; deliberately not in the generic `settings` registry): `catalog.barcode_mode` = `sequence` (default) | `ean13`; `catalog.barcode_prefix` (sequence: 1-8 chars A-Z/0-9 stored upper-case, default `200`; ean13: 200-299); `catalog.barcode_width` (digits of the running number, 4-10, default 6); `catalog.barcode_seq` (last number issued).
- **sequence**: code = `<prefix><number zero-padded to width>`, no check digit, printed as Code 128: `200000001`, `200000002` ... or `VM000001`, `VM000002`. The prefix never changes, only the suffix counts up by one. **ean13**: the earlier behaviour, `prefix + 9-digit number + GTIN check digit` (`2000000000015`, `2000000000022`).
- **Refused combinations** (sequence, all-digit prefix): a total length of 8, 11, 12, 13 or 14 digits (readers, `validateBarcode` and `pos/codes.ts` treat those as EAN-8 / UPC-A / EAN-13 / GTIN-14 or as a GTIN without its check digit) and a prefix starting with 0. A prefix containing a letter may use any width. A generated code never contains `-`, so it can never be a unit code.
- **Next number** = `max(counter, highest existing code of this exact prefix + width) + 1`, skipping numbers already used as barcode, alias barcode or SKU. When the width is used up it throws `CONFLICT` `details.code:'BARCODE_SEQ_EXHAUSTED'` (never a longer suffix). Changing mode / prefix / width affects only future codes: existing barcodes (including old EAN-13) are never rewritten and keep scanning; the counter continues.
- **Transactions**: `nextBarcode()` consumes the number and must run inside the transaction that stores the code (a rollback gives the number back: gap-free). `generateBarcode({exclude?})` only PREVIEWS the next code for an unsaved variant; it is consumed (`claimBarcode`) when the product is saved with exactly that code, and uniqueness is enforced at save. `catalog.barcodePreview({mode,prefix,width})` returns `{valid, error, field, example, exampleNext, next, last, remaining}` for the dialog's live example; `getSettings` adds `barcodeMode`, `barcodeWidth`, `barcodeSeq`, `nextBarcode`, `barcodeError`.
- **One namespace**: `barcodeOwner(code)` reports a primary barcode, an alias or another item's SKU (`via`); a barcode equal to another item's SKU (and the reverse, `SKU_IS_BARCODE`) and a barcode / SKU shaped like a tracked product's unit code (`UNIT_NAMESPACE`) are refused on save, import and in the spreadsheet.
- **Scan resolution** (`core/lookup.ts` `findVariantByScan`): `pos/codes.ts` `scanCandidates` gives every spelling a tier: 0 = the scanned text, 1 = the same symbol written differently (decorations, AIM / GS1, UPC-A <-> EAN-13 / GTIN-14 padding, UPC-E, letter case), 2 = repair guess (check digit dropped / added, leading zeros lost). The best tier with a match wins; when one tier matches two different items the scan throws `CONFLICT` `details.code:'SCAN_AMBIGUOUS'` (`details.matches`) instead of picking one. `lookup.search` matches every word separately (any order), escapes `%` / `_`, and finds alias barcodes for code-like terms.

## Print darkness & barcode dot-snapping
Per printer profile (`printer_profiles.calibration_json`, `Calibration` / `parseCalibration` in `printing/adapter.ts`, no schema change): `darkness` 1-9 (5 = normal), `logoBrightness` 1-9 (5 = follow darkness), `dpi` 203 | 300 | 600 (203 default), `densityCommand` (raw only, default true). Edited under Printing > Printers ("Save and test print"); the test page prints the level, a small-text / solid-bar sample and a sample barcode (`TEST-1234`).
- **Level 5 is a no-op on both paths**: `darknessCss(5)` is `''` (so `prepareHtml` adds nothing) and the ESC/POS builders add no bytes. Keep it that way: tests pin HTML and byte identity.
- **Windows-driver path** (`prepareHtml` -> `<style id="darkness">`): darker = hairline `-webkit-text-stroke` in `currentColor` (0.1 pt per level), lighter = paper-white stroke over the glyphs (0.08 pt per level), logo = `img{filter:brightness() contrast()}`. Pure black/white only (thermal drivers dither grey into speckle) and nothing that changes layout (no font-weight/size/border), so a label that fitted still fits. Receipt / label / test-page layouts themselves use only `#000` / `#fff` and rules >= 0.25 mm; A4/A5/report keep their greys (laser/inkjet).
- **Raw ESC/POS path** (`escpos.ts`): logo raster threshold `160 + 15 x (level - 5)`; `ESC G 1` double-strike at levels 7-9; `GS ( K` fn 49 density step (-6..+6) right after `ESC @` unless `densityCommand:false`. There is no portable command for lighter text.
- **Barcodes / QR are never touched by darkness**: the CSS filter targets `<img>` only and a guard rule forbids filter / stroke on `svg.barcode` / `svg.qr`. Never add a rule that reaches them.
- **Dot snapping** (`printing/barcode.ts`): a module is a whole number of printer dots, one dot = `25.4 / dpi` CSS mm; `fitModules` picks the largest count that fits (cap 0.5 mm = 4 / 6 / 12 dots at 203 / 300 / 600 dpi, floor 0.125 mm = 1 / 2 / 3 dots), centres the symbol and moves it onto a dot boundary of the page. Quiet zones: EAN-13 11+11 (11+7 when that is what fits), others 10+10. `pickFormat`: EAN-13 / UPC-A / EAN-8 only for a complete number with a valid check digit, otherwise Code 128 (jsbarcode auto = code set C for digit runs). `barcodeSymbol` returns `problem`: `too_long` (no bars are drawn), `narrow` (< 0.25 mm), `not_encodable`; `renderLabels` / `printing.renderLabelHtml` report them in `warnings: string[]` and the label dialog asks before printing. Bar height floor: 6 mm or 15 % of the symbol width.
- `renderLabelHtml` sizes bars for the default label printer profile (A4 profile for label sheets); at print time `prepareHtml` re-snaps every `svg.barcode[data-fit]` to the profile actually used (`snapBarcodes`: dpi, scale, X offset). A profile scale other than 100 % is compensated, but keep 100 % on label printers.
- One label per page is laid out 0.5 mm shorter than the label (`LABEL_PAGE_SLACK_MM`): a driver page slightly shorter than nominal otherwise feeds a blank label after every label.
- Print flow: `print()` falls back to the Windows default printer when the profile's device no longer exists, or to the default profile when a remembered profile id was deleted, and returns `{ ok:true, warning }` (raw jobs are never redirected); failed jobs keep page size + copies for Retry; landscape = wide `@page` size + `landscape` flag with the portrait sheet; a silent job is abandoned after 60 s (10 min with the Windows dialog). `printing.printLook({ paper, printerProfileId? })` gives previews the darkness CSS.
